# 内容管理系统详细架构

## 1. 当前架构结论

本仓库当前主线已经切换到 CMS V2。

明确结论：

- 第一版前端已经废弃。
- 第一版后端已经废弃。
- 新前端只能对接 CMS V2 后端。
- V1 页面、V1 接口、V1 静态资源只作为历史参考，不再作为当前架构基础。

当前全局阶段 1 只做文档清理：

- 不创建前端工程
- 不修改 `VSTO/`
- 不修改 `Word本地文件操作核心库/`
- 不修改 V1 后端业务代码与项目文件

当前系统是：

> 面向高中物理教学的本地讲义内容管理与编排系统。

它不是：

- 普通题库 CRUD 后台
- 多人 SaaS 系统
- 在旧静态页面上持续修补的网页集合

## 2. 当前主线工程结构

当前主线工程：

- `src-v2/WordSolution.CmsV2.Domain`
- `src-v2/WordSolution.CmsV2.Application`
- `src-v2/WordSolution.CmsV2.Infrastructure`
- `src-v2/WordSolution.CmsV2.Api`
- `src-v2/WordSolution.CmsV2.Tests`

历史保留工程：

- `题库核心`
- `题库应用`
- `题库基础设施`
- `题库本地服务`
- `题库本地服务/wwwroot`

- `Word本地文件操作核心库`
- `Core.QuestionBank`
- `TagRunner`
- `tools/旧题库迁移工具`

这些历史保留工程不再承接新的主线前后端开发。

## 3. 当前依赖方向

```text
V2 Frontend
  -> WordSolution.CmsV2.Api
      -> WordSolution.CmsV2.Application
          -> WordSolution.CmsV2.Domain

WordSolution.CmsV2.Infrastructure
  -> WordSolution.CmsV2.Domain

WordSolution.CmsV2.Api
  -> WordSolution.CmsV2.Application
  -> WordSolution.CmsV2.Infrastructure
```

约束：

- `Application` 不直接依赖 `Infrastructure`
- `Domain` 不依赖任何上层
- 新前端不直接接数据库、不直接碰文件资产

## 4. 系统核心对象

### 4.1 TeachingTopic

表示教学内容在知识结构中的定位。

示例：

```text
功能关系
机械能守恒
竖直圆轨道
杆模型
球模型
```

职责：

- 提供教学主题定位
- 承载浏览器工作台导航语义

不承载：

- 内容块版本
- 讲义版本
- 生成记录

### 4.2 ContentBlock

可复用内容资产，主资产以 `.docx` 保存。

常见类型：

- 知识点
- 例题
- 练习
- 方法总结
- 普通说明
- 组合型内容块

### 4.3 AtomicSection

小的教学组织片段，用于承接多个内容块的局部编排。

### 4.4 Section

回答的问题是：

> 这个教学主题应该怎么讲？

### 4.5 SectionVariant

同一个 Section 的不同教学用途变体。

例如：

- 基础讲解版
- 提高班版
- 一轮复习版

### 4.6 Handout

回答的问题是：

> 这份材料属于哪类输出对象？

### 4.7 HandoutVersion

回答的问题是：

> 这份讲义当前要按什么结构输出？

### 4.8 OutputForm / OutputTemplate / GeneratedFile

用于输出编排、模板套用和最终生成记录。

### 4.9 TeachingNote

用于承载教学备注、修订建议和讲解提醒。

## 5. 当前 V2 数据与文件边界

### 5.1 数据库

V2 主数据库：

```text
cms-v2.db
```

明确约束：

- 不读取 `question-bank.db`
- 不修改 `question-bank.db`
- 不为旧数据库做兼容层

### 5.2 文件资产

当前 V2 文件资产围绕内容块和讲义输出组织。

典型结构：

```text
{bankRootDirectory}
  cms-v2.db
  content-blocks/
    source/{ContentBlockId}/v{VersionNumber}.docx
    html/{ContentBlockId}/v{VersionNumber}.html
    text/{ContentBlockId}/v{VersionNumber}.txt
  handouts/
    generated/{HandoutVersionId}/*.docx
```

例如：

## 当前定稿：SectionVariant 与 SectionItem 选择模型

更新时间：2026-06-22。以下规则来自 `SectionVariant-开发文档完善依据-定稿.md`，是后续 SectionVariant 设计、前端交互和 CMS V2 API 补齐的依据。

### 1. Section 与 SectionVariant 的关系

`Section` 本身就是“上帝小节”：完整知识池、完整教学结构、完整教学内容组织。`SectionVariant` 不是另一个“上帝版本”，而是从 `Section` 派生出来的教学用途方案，例如基础讲解版、提高版、一轮复习版、冲刺版。

```text
TeachingTopic
  -> Section（上帝小节 / 完整知识池 / 完整教学结构）
       -> SectionVariant（基础讲解版）
       -> SectionVariant（提高版）
       -> SectionVariant（一轮复习版）
```

### 2. SectionVariant 只选择 SectionItem

`SectionVariant` 不重新定义内容结构，不复制 `ContentBlock` / `AtomicSection`，也不提交重构后的前端 flow。

正确模型是：

```text
Section
  -> SectionItem

SectionVariant
  -> SectionVariantItem
       -> SectionItemId
```

因此创建 SectionVariant 时，前端最终提交的是：

```text
selectedSectionItemIds: number[]
```

不得提交：

```text
contentBlockIds
atomicSectionIds
flowItems
重新组装后的树结构
```

这样可以处理同一个 `ContentBlock` 或 `AtomicSection` 在同一个 `Section` 中出现多次的情况，因为真正被选中的是某一次出现，也就是 `SectionItem.Id`。

### 3. CompositeBlock 不是后端 TargetType

`CompositeBlock` 是前端对组类型 `ContentBlock` 的展示组件，不是独立领域模型，也不是 `SectionItem.TargetType`。

后端 `SectionItem.TargetType` 第一版只允许：

```text
ContentBlock
AtomicSection
```

当 `ContentBlock.BlockType` 为以下类型时，前端可以用 `CompositeBlock` 组件展示：

```text
ExampleGroup
ExerciseGroup
VariantGroup
```

文档或代码中不得把 `CompositeBlock` 写成第三种 `SectionItem.TargetType`。

### 4. Difficulty 统一归属

`Difficulty` 是一套共享枚举，允许出现在：

```text
Section
SectionVariant
AtomicSection
ContentBlock
```

不允许出现在：

```text
SectionItem
AtomicSectionItem
ContentBlockVersion
HandoutVersion
SectionVariantItem
```

当前 `AtomicSection` 已经具备 `Difficulty` 字段；后续文档不应再把它写成缺口。

### 5. 第一版默认选择规则

SectionVariant 创建第一版只按“目标顶层项自身难度”做默认选择。

顶层项定义严格为：

```text
SectionItem.ParentItemId == null
```

默认选择只检查：

- 顶层 `ContentBlock`：使用 `ContentBlock.Difficulty`。
- 顶层 `CompositeBlock`：本质仍是 `ContentBlock`，使用父 `ContentBlock.Difficulty`。
- 顶层 `AtomicSection`：使用 `AtomicSection.Difficulty`。

不使用：

```text
SectionVariant.Type
SectionItem.SelectionLayer
SectionItem.TeachingUseOverride
ContentBlock.BlockType
AtomicSection.Type
Section.Difficulty
```

难度包含规则：

```text
Basic    -> Basic
Medium   -> Basic + Medium
Advanced -> Basic + Medium + Advanced
Top      -> Basic + Medium + Advanced + Top
Unset    -> 永不默认选中
```

### 6. 第一版只选择顶层项

第一版 `SectionVariantItem` 只引用顶层 `SectionItem`。`AtomicSection` 内部的 `AtomicSectionItem` 和 `CompositeBlock` 内部的 `ContentBlockRelation` 只作为展开预览显示，不作为独立勾选对象。

未来如需支持“同一个 AtomicSection 下部分选择”，必须以 `SectionVariantItem` 为锚点扩展：

```text
SectionVariantItem
  SelectionMode: Whole | Partial

SectionVariantAtomicItemSelection
  SectionVariantItemId
  AtomicSectionItemId
  SortOrder
  Note
  UpdatedTime
```

不能只用 `SectionVariantId + AtomicSectionId` 表达部分选择，因为同一个 `AtomicSection` 可能通过不同 `SectionItem` 在同一个 `Section` 中出现多次。

### 7. 第一版创建入口

第一版唯一业务入口：

```text
SectionPage -> SectionTree -> Section 根节点右键菜单 -> 新建 SectionVariant
```

不得放在顶部 Toolbar、TeachingStructureTree、Workspace、Inspector 或其他节点右键菜单中。

### 8. 创建流程与后端职责

SectionVariant 创建分两步：

```text
Step 1: 填写 SectionVariant 元数据
Step 2: 进入 VariantSelectionMode 勾选顶层 SectionItem
```

第一步字段：

- `Title`：必填。
- `Type`：必填。
- `Difficulty`：必填，只允许 `Basic / Medium / Advanced / Top`。
- `Description`：可选。

第一版前端不提交：

```text
Status
SortOrder
```

后端默认：

```text
Status = Draft
SortOrder = 当前 Section 下最大值 + 1
```

选择预览由后端计算：

```text
POST /api/cms-v2/section-variants/selection-preview
```

创建提交由后端一次事务完成：

```text
POST /api/cms-v2/section-variants
```

请求核心字段：

```text
sectionId
title
description?
type
difficulty
selectedSectionItemIds[]
```

允许 `selectedSectionItemIds` 为空，即允许创建空 `SectionVariant`。

后端必须重新校验所有选择项，不信任前端预览结果。创建失败时不得留下半成品 `SectionVariant` 或 `SectionVariantItem`。

### 9. 创建成功后的页面行为

创建成功后：

- 重新读取当前 `Section` 相关数据。
- 刷新 `SectionTree` / Variant 展示。
- 新建 `SectionVariant` 可见。
- 不自动打开新建 `SectionVariant`。
- 不自动选中新建 `SectionVariant`。

创建失败后：

- 保留用户填写的元数据。
- 保留当前选择状态。
- 显示整体错误。
- 不做 optimistic update。

## Handout 第一版上线模型定稿

本节记录 `CMS V2 Handout` 第一版的正式目标模型。它覆盖旧的“HandoutVersionItem 只允许 SectionVariant / ContentBlock”口径。

### 1. 核心对象

```text
Handout
  -> HandoutVersion
    -> HandoutVersionItem
    -> OutputForm
      -> GeneratedFile
```

- `Handout` 表示一组相关讲义的总入口，不直接保存编排项。
- `HandoutVersion` 是第一版 `HandoutPage` 的核心工作对象。
- `HandoutVersionItem` 是讲义版本中的顶层引用出现。
- `OutputForm` 驱动输出。
- `GeneratedFile` 记录一次成功生成结果和 `VersionManifestJson`。

### 2. HandoutVersionItem 目标类型

第一版允许：

```text
SectionVariant
AtomicSection
ContentBlock
```

第一版禁止：

```text
Section
SectionItem
AtomicSectionItem
TeachingTopic
ContentBlockVersion
```

语义：

- `SectionVariant`：保存引用，生成时展开其 `SectionVariantItem -> SectionItem`。
- `AtomicSection`：可以被讲义直接引用，生成时整体展开其 `AtomicSectionItem`，不创建 `SectionItem`，不反向修改源 `Section`。
- `ContentBlock`：可以作为讲义级补充直接引用，第一版使用当前版本，不做版本锁定。

### 3. HandoutPage 页面模式

```text
左侧：HandoutStructurePanel
中间：HandoutWorkspace
右侧：HandoutInspectorAndOutput
```

添加入口只在左侧树：

- 根节点：添加到末尾。
- 顶层 `HandoutVersionItem`：在此后添加。
- 内部派生节点：只读，不提供添加入口。

### 4. OutputTemplate / OutputForm / GeneratedFile

- `OutputTemplate` 是本地 DOCX 模板，承载页面设置、页眉页脚、样式和编号。
- 第一版 `OutputForm` 只允许 Word。
- `Audience` / `VisibilityMode` 第一版只作为元数据，不做实际内容过滤。
- 成功生成写入 `GeneratedFile`。
- 失败不写 `GeneratedFile`，也不做失败历史。

### 5. Word 生成关键规则

第一版生成不能只依赖扁平 `AppendDocument(KeepSourceFormatting)`。

必须引入结构化 Render Plan，并处理：

- `TeachingTopic` -> 标题 1。
- `Section` -> 标题 2。
- `AtomicSection` -> 标题 3。
- 题干 -> 统一“例题”样式。
- 模板页眉页脚保留。
- 源 DOCX 页眉页脚忽略或清除。
- 跨 DOCX 合并后的例题编号全文连续。

在正式实现前必须做编号技术 Spike，使用多源 DOCX fixture 验证编号 `1..n` 连续。
