# SectionPage Development Specification

## 1. Purpose

This document defines the first implementation target for `SectionPage` in the CMS V2 frontend.

`SectionPage` is not a generic CRUD page.

It is a teaching-structure workspace for efficient lesson preparation.

The page should help the user:

- arrange teaching content;
- edit ContentBlocks through Word;
- gradually form AtomicSections from existing blocks;
- navigate teaching structure quickly;
- manage attention by hiding irrelevant structure;
- prepare a Section that can later be reused by HandoutPage.

The first version should focus on making `SectionPage` usable as soon as possible. Do not overdesign HandoutPage now.

---

## 2. Core Concepts

### 2.1 ContentBlock

`ContentBlock` is the actual editable content asset.

Examples:

- Question;
- Knowledge point;
- Method summary;
- Note;
- Example group / composite block.

A `ContentBlock` owns the Word document content.

Editing the body of a block means opening its `.docx` in Word, editing it, saving it, closing Word, and refreshing the preview.

### 2.2 SectionItem

`SectionItem` is not the actual body content.

It is an occurrence/reference inside a Section.

A SectionItem references:

- a ContentBlock;
- or an AtomicSection;
- or another allowed target type.

Do not treat SectionItem as storing body content.

### 2.3 AtomicSection

`AtomicSection` is the smallest teaching unit.

It is a free teaching container, not a fixed template.

It should not force a structure such as:

```text
KnowledgePoint -> TypicalExample -> Example -> Variant
```

Instead, it should allow the user to gradually organize existing content into a meaningful teaching unit.

An AtomicSection may contain:

- knowledge blocks;
- questions;
- groups;
- summaries;
- notes;
- other allowed non-AtomicSection blocks.

AtomicSection itself can have a difficulty value.

ContentBlocks inside it can also have difficulty values.

Future handout generation may use difficulty to automatically select suitable content.

### 2.4 CompositeBlock / GroupBlock

A CompositeBlock is a grouping structure such as an example group, exercise group, or variant group.

It is visually similar to AtomicSection, but semantically different.

A CompositeBlock may be rendered with the same base container component as AtomicSection.

### 2.5 Section

`Section` is the formal teaching structure editing target.

It is not the final handout output.

The purpose of Section is to answer:

```text
How should this teaching topic be taught?
```

---

## 3. Page-Level Design Principle

The center of attention must always be the main editing workspace.

Secondary areas such as:

- pending AtomicSections;
- temporary question staging area;
- material inbox;
- advanced metadata;

must not become permanent primary regions in the first version.

They may appear as:

- toolbar entries;
- drawers;
- dialogs;
- secondary panels.

---

## 4. Overall Layout

The page layout is:

```text
SectionPage

├── SectionTopToolbar
└── SectionMainLayout
    ├── TeachingStructurePanel
    ├── SectionWorkspace
    └── SectionInspector
```

Visual structure:

```text
┌─────────────────────────────────────────────────────────┐
│ SectionTopToolbar                                       │
├───────────────┬────────────────────────────┬────────────┤
│ Structure     │ SectionWorkspace           │ Inspector  │
│ Panel         │ Main content area          │ Panel      │
│               │                            │            │
└───────────────┴────────────────────────────┴────────────┘
```

### 4.1 Left Area: TeachingStructurePanel

The left panel is for structure navigation.

It should support three display modes:

```text
Hidden
Docked
Focused
```

### 4.2 Center Area: SectionWorkspace

The center area is the main working area.

It should occupy all remaining flexible width.

It displays a document-like teaching content flow.

### 4.3 Right Area: SectionInspector

The right panel is for selected-object properties.

It should have fixed width and be collapsible.

It should not edit Word body content.

---

## 5. SectionTopToolbar

### 5.1 Responsibility

`SectionTopToolbar` controls page-level actions and mode switches.

It should not become a crowded command bar.

### 5.2 Suggested Content

First-level toolbar content:

- current Section title;
- save / sync status;
- preview entry;
- teaching note mode toggle;
- structure panel toggle;
- inspector toggle;
- temporary question staging entry;
- pending AtomicSection entry;
- more menu.

### 5.3 Rule

Only high-frequency controls should be visible directly.

Low-frequency functions should go into `More`.

---

## 6. TeachingStructurePanel

### 6.1 Purpose

The tree in this panel is not a raw ContentBlock tree.

It is a teaching navigation tree.

It should help the user:

1. quickly preview what teaching units are under a node;
2. see what kinds of blocks each teaching unit contains;
3. browse sections under a chapter/topic;
4. create, delete, rename, reorder sections;
5. quickly enter a Section;
6. locate content inside the central workspace;
7. focus on a node as the temporary root.

### 6.2 What the Tree Should Show

The tree should primarily show teaching units and teaching structure.

It should show:

- chapter/topic nodes;
- Section nodes;
- AtomicSection nodes;
- major structure nodes;
- statistics of contained blocks.

It should not show individual question ContentBlocks in detail.

For questions, show statistics only:

```text
Questions: 5
Typical examples: 1
Variant exercises: 3
```

Do not display all question titles in the tree by default.

### 6.3 Docked Mode

Docked mode should be concise.

It should mainly show names for quick positioning.

Example:

```text
Circular Motion
  Centripetal Force
  Conical Pendulum
  Critical Motion
```

### 6.4 Focused Mode

Focused mode should provide more structural detail.

It may show:

- title;
- difficulty;
- question count;
- knowledge point count;
- exercise group count;
- variant count;
- future frequency / importance indicators.

Example:

```text
Centripetal Force Basics
  Difficulty: Medium
  Questions: 6
  Knowledge Points: 2
  Variants: 3
```

### 6.5 Positioning Behavior

In all modes, clicking a tree node should locate the corresponding content in `SectionWorkspace`.

Tree click should normally mean:

```text
Tree node selected
↓
Workspace scrolls to corresponding position
↓
Corresponding item becomes selected
↓
Inspector updates
```

Do not treat tree click as page navigation unless the clicked item is a different Section.

### 6.6 Hidden / Docked / Focused Modes

#### Hidden

The structure panel is collapsed.

The workspace receives maximum width.

A narrow trigger or icon should remain.

#### Docked

The structure panel is fixed on the left.

It has fixed width.

It is used for lightweight navigation.

#### Focused

Focused mode is a structure focus view.

It can be triggered by:

- hovering near the left edge;
- clicking a structure button;
- future shortcut.

Focused mode should visually emphasize the tree:

- wider panel;
- floating layer;
- shadow;
- background dimming;
- more detailed information.

The purpose is not necessarily editing the tree.

The purpose is to focus attention on structure and show more structure information.

### 6.7 Tree Component Layering

All future trees should share the same focus-root capability.

Do not implement focus-root logic only for SectionPage.

Tree architecture:

```text
BusinessTree
↓
FocusTree
↓
TreeNode / TreeRenderer / low-level UI
```

Examples:

```text
TeachingStructureTree
TagTree
ContentBlockTree
KnowledgeTree
```

Business trees use FocusTree.

They do not inherit FocusTree.

### 6.8 Focus Root Capability

FocusTree must support promoting a node to the temporary display root.

This is used for attention management.

Example:

```text
Full tree:
Book
  Chapter
    Section
      AtomicSection
```

When `Chapter` is promoted to root:

```text
Chapter
  Section
    AtomicSection
```

Unrelated branches are hidden.

### 6.9 Root Promotion Restrictions

Not every node may be promoted to root.

The business tree must define which node types are promotable.

For SectionPage / TeachingStructureTree:

Allowed examples:

- TeachingTopic;
- Chapter;
- Section;
- AtomicSection, if useful;

Disallowed examples:

- individual Question ContentBlock;
- ExampleGroup / CompositeBlock if it is too small or too low-level;
- any node type that should not become a focus workspace root.

Important rule:

```text
ExampleGroup should not be allowed to become a root node.
```

The restriction should not be hardcoded inside FocusTree.

It should be passed by business configuration, for example:

```text
canPromoteToRoot(node) => boolean
```

or:

```text
promotableNodeTypes = [...]
```

FocusTree provides the mechanism.

BusinessTree decides the rule.

## 7. SectionWorkspace

### 7.1 Purpose

`SectionWorkspace` is the main editing area.

It is a document-like teaching content flow.

It is not:

- a table;
- a card wall;
- a backend management list;
- a pure tree editor.

It should feel closer to:

```text
Notion / document flow / teaching handout draft
```

but with block-level operations.

### 7.2 Core Display Model

Workspace displays a unified ordered flow of SectionItems.

Do not divide the workspace into separate lists by type.

Correct model:

```text
SectionContentFlow

1. ContentBlockDisplay
2. ContentBlockDisplay
3. AtomicSectionBlock
   3.1 ContentBlockDisplay
   3.2 ContentBlockDisplay
4. CompositeBlock
   4.1 ContentBlockDisplay
5. ContentBlockDisplay
```

Wrong model:

```text
RootContentList
AtomicSectionList
CompositeBlockList
```

All items appear in teaching order from top to bottom.

### 7.3 Workspace Columns

Workspace should support two modes:

#### Clean Mode

Only content column is visible.

The document content gets maximum focus.

#### Teaching Note Mode

Workspace is divided into:

```text
MainContentColumn | TeachingNoteColumn
```

The note column shows teaching notes anchored beside related blocks.

This is not the same as `SectionInspector`.

`SectionInspector` edits properties.

TeachingNoteColumn supports contextual reading and teaching reflection.

### 7.4 SectionFlowItem

`SectionFlowItem` is the wrapper for one item in the ordered flow.

It may render:

- ContentBlockDisplay;
- AtomicSectionBlock;
- CompositeBlock;
- future allowed structures.

---

## 8. ContentBlockDisplay

### 8.1 Name

Prefer:

```text
ContentBlockDisplay
```

or:

```text
ContentBlockView
```

Avoid:

```text
ContentBlockCard
```

because “card” may cause Codex to design a backend-style card.

### 8.2 Purpose

`ContentBlockDisplay` displays full content preview inside the workspace.

It should show the actual body preview, not only a title or summary.

### 8.3 Visual Style

ContentBlockDisplay should be document-like.

Do not use heavy card styling.

Avoid:

- strong borders;
- heavy shadows;
- large background blocks;
- huge gaps.

Use:

- vertical spacing;
- hover highlight;
- selected highlight;
- lightweight handle / action area.

It should be similar to Notion blocks.

### 8.4 Main Structure

Suggested internal structure:

```text
ContentBlockDisplay
├── BlockHoverHandle
├── ContentBlockPreview
└── InlineActionArea
```

### 8.5 High-Frequency Actions

The component should support high-frequency actions:

- Edit in Word;
- Refresh preview;
- Move up;
- Move down;
- More menu;
- quick difficulty adjustment;
- quick teaching-use adjustment, if needed.

Actions should not dominate normal reading.

Prefer showing actions on hover or selected state.

### 8.6 Difficulty

Difficulty is an important property.

It should be visible or quickly inferable in the block UI.

It may affect:

- small badge;
- left side indicator;
- subtle background;
- tiny corner marker;
- future sorting/filtering/generation.

Do not use large visual effects that destroy document reading.

Difficulty should be quickly editable from the block itself, because the user expects to adjust it often.

### 8.7 Responsibility Boundary

ContentBlockDisplay may trigger business actions, but should not scatter raw API calls.

Use:

```text
useContentBlockWordEditor()
```

or other composables.

ContentBlockDisplay should not directly implement low-level editing-session polling logic.

---

## 9. AtomicSectionBlock

### 9.1 Purpose

`AtomicSectionBlock` represents an AtomicSection inside the document flow.

It is a teaching-unit container.

It does not directly edit body content.

Its children ContentBlocks provide the actual body previews.

### 9.2 Visual Form

AtomicSection should use a weak container boundary.

The title and actions should be attached to the border line.

Example:

```text
┌── AtomicSection: Centripetal Force Basics ───── [actions] ┐

  ContentBlockDisplay

  ContentBlockDisplay

└───────────────────────────────────────────────────────────┘
```

### 9.3 Border Rule

Use weak border, not heavy card.

The border expresses grouping and ownership.

It should not make the workspace look like nested backend cards.

### 9.4 Inner Layout

Children should use micro-indent.

Do not use deep tree-like indentation.

### 9.5 Header Actions Slot

The header action area must be implemented as a slot.

Do not hardcode all buttons.

Future actions may include:

- rename;
- collapse / expand;
- move;
- add note;
- AI analysis;
- generate summary;
- convert;
- custom commands.

### 9.6 AtomicSection Difficulty

AtomicSection itself can have difficulty.

This difficulty may be used later for filtering/generating handouts.

---

## 10. CompositeBlock / GroupBlock

CompositeBlock should share the same container visual style as AtomicSection.

Use a reusable base component.

It is not allowed to become the root of FocusTree unless business rules explicitly allow it.

For the current design, ExampleGroup should not be promotable to root.

---

## 11. StructuredContainer

A reusable container component should be created for AtomicSection and CompositeBlock.

Suggested structure:

```text
StructuredContainer
├── InlineBorderHeader
│   ├── title
│   └── actions slot
└── body slot
```

### 11.1 InlineBorderHeader

This component renders the title and action slot on the border line.

It can be reused by:

- AtomicSectionBlock;
- CompositeBlock;
- future group structures.

Do not use it for ContentBlockDisplay.

ContentBlockDisplay is body content, not a structure container.

---

## 12. InsertPoint

### 12.1 Purpose

`InsertPoint` is a reusable interaction component.

It appears between two flow items.

When the mouse stays between blocks for a short time, it displays an insert button.

### 12.2 Responsibility

InsertPoint only means:

```text
Something can be inserted here.
```

It does not decide what can be inserted.

It does not call APIs.

It emits insert context to the parent.

### 12.3 Usage

It should be usable in:

- SectionContentFlow;
- AtomicSectionBlock inner flow;
- CompositeBlock inner flow;
- future HandoutPage.

Example:

```text
SectionFlowItem
InsertPoint
SectionFlowItem
InsertPoint
SectionFlowItem
```

### 12.4 Dynamic Insert Menu

The parent component generates allowed insert types based on context.

Do not hardcode three options only.

The menu must show all structures allowed at the current insertion point.

For example, at Section root level it may show:

- KnowledgePoint;
- Question;
- CompositeBlock / Group;
- AtomicSection, if direct insertion is allowed in later versions;
- existing content reference, in later versions;
- existing AtomicSection reference, in later versions.

Inside AtomicSection:

- ContentBlock types are allowed;
- CompositeBlock may be allowed;
- AtomicSection must not be allowed.

### 12.5 AtomicSection Nesting Rule

AtomicSection is the smallest teaching unit.

Do not allow AtomicSection inside AtomicSection.

## 13. Insertion Flow

### 13.1 First Version Goal

The first version should support inserting blank content and editing it through Word.

The first version does not need to support selecting existing questions from a populated database.

Later versions must support inserting existing:

- questions;
- groups;
- AtomicSections;
- other content assets.

### 13.2 Insert New Blank Content Flow

The correct logic is:

```text
Choose insert position
↓
Choose allowed type
↓
Create ContentBlock in content library / backend asset area
↓
Create SectionItem referencing the new ContentBlock
↓
Insert SectionItem at selected position
↓
Select new item
↓
Open Word edit session
↓
User edits and saves
↓
System syncs new version
↓
Refresh ContentBlockDisplay preview
```

Do not think of SectionItem as containing body text.

### 13.3 Auto-Filled Form Context

The form should display user-friendly names, not raw IDs.

Displayed fields should look like:

```text
Current Section: Circular Motion
Parent: Centripetal Force Basics
Insert Position: After “Typical Example 1”
Type: Question
```

Internally, the system submits:

```text
sectionId
parentItemId
targetType
targetId
sortOrder
contentBlockType
```

### 13.4 First Version Form Rule

Auto-filled context fields should be read-only in v0.1.

Later versions may allow advanced users to change them manually.

Reserve the design space for later manual override.

---

## 14. Wrap as AtomicSection

### 14.1 Purpose

The system should support forming AtomicSections from existing blocks.

This matches the intended workflow:

```text
First create content
↓
Then discover structure
↓
Then wrap content into AtomicSection
```

### 14.2 v0.1 Scope

First version supports only continuous selection.

Example:

```text
A
B
C
D
E
```

Select B, C, D:

```text
A
AtomicSection
  B
  C
  D
E
```

The new AtomicSection appears at the position of the first selected block.

### 14.3 Non-Continuous Selection

Future versions may support selecting non-continuous blocks.

Example:

```text
Select B, D, F
```

Then:

- AtomicSection appears at B's original position;
- internal order follows original document order, not click order.

This is higher risk and should not be implemented in v0.1.

Risks include:

- sorting bugs;
- parent change bugs;
- selected state bugs;
- rollback bugs;
- inconsistent SortOrder.

### 14.4 Backend / Use Case Requirement

Wrapping blocks as AtomicSection should eventually be a backend use case.

Do not let the frontend manually perform many fragile API calls to reorder and reparent items.

## 15. Word Editing Flow

### 15.1 Decision

V2 v0.1 should inherit the proven product behavior of the historical editing-session workflow, but the implementation must be built on V2 backend capabilities.

Do not redesign the Word editing chain from scratch.

### 15.2 Desired User Experience

```text
Click Edit in Word
↓
Word opens
↓
User edits content
↓
User saves and closes Word
↓
System detects changes
↓
System creates new version
↓
System regenerates HTML preview
↓
ContentBlockDisplay refreshes automatically
```

### 15.3 Implementation Direction

Use an editing-session abstraction.

Frontend should call a use-case/API to create an edit session.

The edit session is responsible for:

- preparing a temporary docx;
- opening Word through the chosen strategy;
- tracking file changes;
- syncing changed file into a new ContentBlockVersion;
- regenerating preview.

### 15.4 Open Word Strategy

Do not hardcode only one open strategy in frontend design.

Define a replaceable Word open strategy.

Possible strategies:

```text
LocalServiceOpenStrategy
OfficeUriOpenStrategy
```

For v0.1, prioritize preserving the tested user experience while using the V2 backend as the only implementation source.

### 15.5 Frontend Responsibility

Frontend should:

- trigger edit session;
- show editing state;
- poll or listen for session status;
- refresh preview when completed;
- show failure state when needed.

Frontend should not:

- directly manipulate local docx files;
- directly inspect Word processes;
- directly generate HTML previews.

### 15.6 Component Encapsulation

Use a composable:

```text
useContentBlockWordEditor()
```

ContentBlockDisplay should call a simple method such as:

```text
openInWord(contentBlockId)
```

Do not scatter session polling logic inside UI components.

## 16. SectionInspector

### 16.1 Purpose

The inspector displays and edits properties of the currently selected object.

It does not edit Word body content.

It does not navigate structure.

### 16.2 Selection-Driven

Inspector follows current selection.

Selecting from tree or workspace should update Inspector.

### 16.3 Stable vs Evolving Properties

Not all important properties are stable yet.

Separate properties into:

```text
Stable properties
Evolving properties
```

Stable examples:

- title;
- description;
- status;
- sort/order information;
- version information.

Evolving examples:

- importance;
- frequency;
- teaching tags;
- teaching suggestions;
- future custom fields.

Do not prematurely hardcode unstable concepts into rigid enums.

### 16.4 High-Frequency vs Low-Frequency Properties

High-frequency properties should be editable directly in ContentBlockDisplay.

Examples:

- difficulty;
- possibly teaching use / teaching role.

Low-frequency or detailed properties belong in Inspector.

Examples:

- title override;
- reference mode;
- locked version;
- long note;
- advanced metadata.

### 16.5 Teaching Notes

Teaching notes appear in two places:

1. in Inspector, for management and editing;
2. beside the content in Teaching Note Mode, for contextual reading.

They are the same underlying notes shown in different forms.

## 17. State Design

### 17.1 Main State Groups

SectionPage should manage:

```text
section
sectionFlowItems
selectedItemId
selectedItemIds
insertContext
leftPanelMode
rightInspectorVisible
teachingNoteMode
editSessions
loading
dirty
```

### 17.2 Multi-Section Future Compatibility

Future versions may support opening multiple Sections at once.

Therefore, avoid naming state as if there can only ever be one Section.

Prefer a structure that can later be grouped by `sectionId`:

```text
sectionWorkspaces: {
  [sectionId]: {
    section,
    sectionFlowItems,
    selectedItemId,
    selectedItemIds,
    insertContext,
    dirty
  }
}
```

v0.1 can still show only one Section.

But the state shape should not block future multiple Section workspaces.

### 17.3 Multiple Word Edit Sessions

The user may later edit multiple ContentBlocks in Word at the same time.

Do not store only:

```text
currentEditSession
```

Prefer:

```text
editSessions: {
  [contentBlockId]: {
    sessionId,
    status,
    sectionId,
    itemId,
    startedAt
  }
}
```

## 21. v0.1 Scope

### Must Do

- SectionPage layout;
- TeachingStructurePanel hidden / docked / focused mode design foundation;
- FocusTree root promotion mechanism with business-level restrictions;
- SectionWorkspace as ordered document flow;
- ContentBlockDisplay with full preview and lightweight actions;
- difficulty quick display and quick edit;
- InsertPoint component;
- dynamic insert menu based on context;
- create blank ContentBlock and create SectionItem reference;
- edit in Word via the V2 editing-session chain that preserves the proven user experience;
- refresh preview after edit session completes;
- continuous selection wrap as AtomicSection;
- StructuredContainer / InlineBorderHeader for AtomicSection and CompositeBlock;
- Inspector for selected-object properties.

### Should Not Do in v0.1

- full HandoutPage;
- complex drag-and-drop;
- non-continuous block wrap as AtomicSection;
- full undo system;
- complete cloud editing support;
- advanced AI actions;
- over-abstracted generic layout framework;
- forced teaching-role template inside AtomicSection;
- hardcoded unstable importance/frequency enum.

---

## 22. Final Principle

SectionPage should help teaching structure emerge naturally from real content.

The system should support:

```text
Create content quickly
↓
Edit content in Word
↓
Preview content in browser
↓
Adjust difficulty and key properties quickly
↓
Organize content into teaching units
↓
Navigate structure without losing attention
```

Do not turn this page into a backend management interface.

Do not force users to make all structural decisions before content exists.
