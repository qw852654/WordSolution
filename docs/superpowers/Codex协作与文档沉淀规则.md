# Codex 协作与文档沉淀规则

## 0. 计划与规格的边界清晰度

- 每一次写开发文档、规格文档或开发计划时，都必须把执行边界写清楚，目标是最大限度防止 Codex 自由发挥。
- 开发计划不能只写阶段标题，必须写清每个阶段允许做什么、明确不允许做什么、涉及哪些文件范围、需要哪些测试与验证、完成后是否需要后端重启、是否可以进入下一阶段。
- 涉及执行线程派发的计划，必须额外写“线程派发边界”或可直接复制的阶段任务说明，确保总控线程拉起执行线程时不只依赖计划标题。
- 对容易误扩展的需求，必须写明反例和禁止项，例如“不做前端”“不改后端”“不新增复杂面板”“不刷新某列表”“不切换视图”“不做后续阶段”等。
- 开发文档描述规格时，要把触发条件、非触发条件、成功行为、失败行为、边界数据、兼容关系和人工验收点写完整；不能只写概念性描述。
- 如果当前讨论中已经确认过取舍，必须沉淀到文档或计划中，不能依赖后续 Codex 记忆。
- 计划越涉及跨前端、后端、API、数据、文档或自动推进，边界越要细；宁可计划偏长，也不要给执行线程留下自由发挥空间。

更新时间：2026-06-25

本文件记录 WordSolution 项目中用户与 Codex 协作时的长期约定。后续需求讨论、规格沉淀、执行计划与开发推进应优先遵守本文件。

## 1. 总体协作方式

- 总控线程主要负责和用户对话、澄清业务需求、确认设计取舍、读取执行线程结果、规划下一步。
- 代码实现、较大范围文档修改、验证与修复，优先在执行线程中完成。
- 如果一个计划需要分阶段推进，优先复用同一个执行线程串行推进，不为每个阶段反复创建新线程。
- 每个阶段完成后，执行线程必须给出清晰结果：完成范围、修改文件、测试结果、是否需要重启后端、是否可以进入下一阶段、仓库状态。
- 总控线程读取结果后，再决定进入下一阶段、安排修复、终止自动推进或请求用户确认。

## 2. 需求讨论规则

- 需求不清楚时，先对齐业务含义，再进入文档或开发。
- Codex 每轮提出问题时，应同时给出自己认为合理的建议，方便用户快速选择。
- 涉及多个方案时，应先说明推荐方案和理由，再列出备选方案及取舍。
- 用户确认前，不直接进入实现。

## 3. 规格文档规则

- 不为每一个小需求新建规格文档。
- 规格优先写入现有模块文档。
- 如果现有文档能够承载新规格，应直接补充到对应模块文档中。
- 只有确实没有合适承载位置时，才允许新建规格文档。
- 新建规格文档前，Codex 必须先说明为什么现有文档放不下，并等待用户确认。
- 新建规格文档应使用清晰中文命名。

## 4. 开发计划规则

- 不为每一个开发任务新建独立计划文件。
- 执行计划统一写入开发计划总文档。
- 如果开发计划总文档不存在，只创建这一份长期总文档。
- 后续新计划以章节形式追加，包含背景、阶段、执行线程、验证方式、人工验收清单。

## 5. 自动推进规则

- heartbeat 只用于阶段巡检和推进，不应在当前阶段未完成时重复发送任务。
- 当前阶段未完成时，heartbeat 应保持静默。
- 如果发现并发执行线程、需求歧义、测试冲突、仓库状态异常、范围失控或需要用户做业务取舍，应终止自动推进并汇报。
- 自动推进结束后，应停止对应 heartbeat，避免继续唤醒。
